# 单算子内核计时

一次处理一个用户指定算子或公开入口，其内部多个 kernel、分支和子模块属于同一任务，沿真实调用链覆盖；不扩展到其他独立算子。完整 wheel 构建与打点范围是两件事。
质量顺序：数值正确、保持原流水与同步、记录可解释。中文交付，API/枚举保留原名；遵守目标仓库的开发与 ABI 规则。

## Step 0：环境、范围和原用例

- 已明确的用户选择直接沿用。芯片未知时先询问 A2/A3/A5，推荐并默认 A5 (`ascend950`)；未答复时可按标注的 A5 假设准备方案，实际构建/运行前核对设备，不能用默认值覆盖探测结果。
- 记录产品型号、构建 SoC、CANN 版本、容器名、容器内仓库/Python 环境和设备号。按工程构建脚本核对映射；本仓 A2=`ascend910b`、A3=`ascend910_93`、A5=`ascend950`，不是所有工程的固定参数。
- 锁定一个公开入口、工程目录、原性能入口/语言、用例文件、生成器、执行器、比较规则与参数。新入口语言与原测试实现一致；缺少 `_torch_adpt.h` 不等于缺少适配层，沿用实际 aclnn/ctypes/Stable ABI/dispatcher/C++ 路径。
- 找不到原性能用例时先确认来源，不自造用例替代；可以继续已授权的分析/源码工作，原用例采集标记待补。
- 应有编译和原用例通道。设备不可用时继续已授权的源码接入与离线检查，记录设备验证待完成，不虚构通过。
- 实施前读 [迁移指南](references/migration-guide.md)。A5 优先检查缓存发布；所有相关平台检查 OPP 初始化、加载产物及关闭行为。

## Step 1：原始流程、方案和选择

修改任何 host、枚举或 kernel 前，追公开入口 → host/tiling → 实际 kernel → AIC/AIV 分支、循环和原同步，明确原用例路由及可能遗漏的实现。
生成 `<算子工程>/docs/timer_flow.md`：原始图以 host 为主线，标注阶段位置、核型、循环轴与完成锚点；提供至少两个有实际区别的粒度方案，每个包含图上 Tik/Tok、枚举清单、Tok 模式与开销取舍。区分 issue window、瞬时点与完成耗时。
用户选定后实施；已有选择沿用，仅覆盖或测量语义实质变化时重新确认。不要照搬模板占位阶段。

## Step 2：诊断接入、布局和打点

- 保留公开调用、参数顺序及默认行为；需要独立 Profile 入口时按仓库 ABI 规则实现，不强行改公开 ABI。只在诊断调用创建独立清零 INT64 timer，验证连续性、大小、设备、对齐及容量。
- 普通调用不自动创建 timer；null/关闭计时不读时钟、不写 GM、不增加计时屏障。多 kernel 使用独立 slice；并发调用及采样不共用仍在执行的存储。
- 复用已有计时器前核对布局、关闭开关与发布；否则按需复制 assets。模板 96 是存储容量，按实际 launch 配置，不是 A5 物理核数。默认映射是一 AIC + 两 AIV，其他比例同时适配映射、容量和解析，越界不回绕。
- Init → NoBarrier Tik → 原业务 → 配对 Tok → 共同收尾；检查所有核型、早退分支。并行在途固定窗口使用独立计时对象。不新增 SyncAll/flags/业务 barrier 来统一时间，复用确认作用域的原锚点；无安全完成锚点时记录 issue window/瞬时点。总窗口或完成测量的局部 drain 经方案确认并注明扰动。
- 动态 iter 使用本核单调轴，核对截断；同槽单轮多次用 Accumulate，其合成 end 只分析 duration，不进绝对时间轴。停测摘打点与计数，保留业务等待。
- `ENABLE_TIMER=0` 真正关闭；`ASCEND_TIMER_EXPLICIT_GM_PUBLISH` 默认 0，确认写入路径、编译配置和目标 API 支持后启用。A5 关闭自动 kernel-end 写回时不能依赖自动发布。
- 全部结束时间戳写完后调用一次 `timerAll.Publish()`，定向发布本核事件与动态计数。定制 metadata 由唯一写者单独发布；只处理 timer 独占 cache line，不刷新整个 DCache，不加跨核同步。

## Step 3：原用例的主要采集入口

在原工程测试目录生成同语言 `profile_performance` 入口，沿用原框架，不固定 ATK/Python。原框架自带的系统 profile 可保留，不另造外部 profiler 流程。
入口自动完成：

1. 检查当前环境、Profile 符号、本轮归档与实际加载的 host/kernel/适配层；不能只凭预检进程 exit 0，必须确认相关 kernel 比对实际执行，缺少 staging/归档等证据标记未验证并先补证据。OPP 在可能初始化 CANN 注册表的导入或设备调用前准备。
2. 执行原性能用例，保留原计时循环、warmup、seed、参数和比较规则；在计时循环外保存真实输入值与全部 kwargs，不替换为相似 shape 的自造数据。
3. 用同份输入独立执行普通对照与诊断采集，沿用原输出比较规则，导出 raw、逐核 CSV、metadata、日志和阶段汇总。失败非零返回并保留 raw/证据。
4. 打印状态、用例、实际路由和绝对结果目录。默认 `<仓库>/profiling_results/<算子>/<run_id>/`，加入工程忽略规则；已有输出约定可保留，但文档提供直接链接。

安装后应一条主要命令完成；需要时至多第二个重放/离线入口，不让用户串接内部脚本。独立重放自行准备 OPP，不依赖另一个进程的环境修改。
默认 cycles。频率未确认不输出伪造 us；Perfetto 同时需要 cycles/us 与相关核型共同时钟确认。Accumulate 不进时间轴，不推断跨 launch/设备间隔。

## Step 4：完整运行说明

用 [运行说明模板](assets/timer_run.md) 生成 `<算子工程>/docs/timer_run.md`，与 timer_flow 同级。交付前替换全部占位与路径，验证实际入口存在：Docker exec → 容器仓库 → 镜像约定的 Python/CANN 激活 → 目标芯片构建 → 本轮准确包安装 → 一个主要入口 → 结果阅读。
沿用工程构建。本仓 wheel 示例明确 SoC，`FLA_NPU_OPS=` 清空遗留筛选以完整构建；其他工程按实际规则。归档必须来自本轮且与 staging 一致，不能按提交号字典序或旧目录最后一个文件选择；构建/安装/测试解释器一致。
给出成功标志、失败日志、已保存输入/raw 的重放及原性能报告路径。保留 kernel 校验和实际路由完整性检查，不跳过预检或放宽缺记录检查来宣称成功。

## Step 5：集中交付与独立审核

固定三份主要文档，算子 README/原测试 README 只提供导航，不复制完整命令：

| 文档 | 内容 |
| --- | --- |
| docs/timer_flow.md | 原流程、选定打点、枚举/布局、测量含义 |
| docs/timer_run.md | 当前有效的 Docker 到采集步骤、主入口、结果位置及排障 |
| docs/timer_report.md | 当前结论、源码审核/设备验证状态、版本和数据链接 |

由未参与实现的独立 agent 对照原图审核位置、所有 Tik/Tok 配对、枚举/解析/清单四方一致，以及关闭行为、容量、发布所有权和原用例入口；按可用环境运行检查，将问题及位置如实写入 timer_report，修复后复核。审核无可用执行能力时记录未完成，不扩展用户执行权限。
报告区分源码检查、模拟、设备采集和正式性能/精度验收。数据记录 SoC/CANN/Python、源码提交、布局、加载路径、包标识、用例 ID、输入哈希和采集选项。仅归纳数据支持的阶段耗时/核间负载，不能把 issue window 或频率假设写成瓶颈。
维护当前有效结论，日志按 run_id 保存；已有历史报告保留并链接。摘要给主入口、timer_run 与结果位置，不以零散 UT 路径替代完整说明。

## 完成检查

- 芯片、单入口、原用例来源及实际路由明确，与用户方案一致。
- ABI/普通行为保留，null/关闭无计时工作，容量/布局/写者/发布/解析匹配。
- 一主入口完成采集；保留 raw/比较/环境与加载证据，缺核/残缺/负时长不静默接受。
- 三份文档同目录，命令可复制，安装本轮准确产物；审核和实测状态如实记录。

模板回归：`python scripts/validate_assets.py`；CANN/NPU 验证在目标环境进行。复杂迁移参考 [历史案例](references/worked-example-fused-attention-op.md)，旧同步、频率和自动分配示例不能覆盖当前要求。
